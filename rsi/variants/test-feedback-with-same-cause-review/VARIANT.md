# Test runs get back the verdict and failing tests their filter cut, and the finish review probes other inputs with the same cause

hypothesis: The parent leaves two things to chance, at opposite ends of a run. In the middle, the agent pipes almost every test run through a filter (`| tail -3`, `| grep -E "^(Ran|OK|FAILED)"`). The filter often cuts the verdict: Django-style runners print "Destroying test database…" after it, and `FAILED (errors=1)` doesn't say which test. So the agent reruns the same suite with a new filter, then again to see the traceback, often only to learn that a guessed label names no module. At the end, its once-per-run finish review only re-checks the issue's own example, so a fix that covers that one way into the bug and misses a second way to the same cause goes out as "minimal". This package puts the two changes together. `extensions/test-feedback.ts` (from test-runs-recover-cut-verdict-and-bad-la, unchanged) tees a filtered test run's full output to /tmp. When the filtered result lacks the verdict or the failing test ids, it adds them and the log path. It also names labels of a `runtests.py`/`unittest` runner that match no module, along with the closest real ones. `extensions/finish-guard.ts` (from finish-review-probes-same-cause-inputs, unchanged except for the shared regex) adds one step to the review when there is a change. The agent names the cause its change removes, then tries 2-4 other inputs that reach the same code by another route in one script. It extends the fix only where the reported problem still shows, and stays on the task's code path. Where the two overlap I kept the code and made one notion of a test command: finish-guard, evidence-marker and test-feedback now share the regex with `\bruntests\b`. That way, the review's "no test command has run since your last edit" agrees with what test-feedback treats as a test run. The parent's prompt, 8K thinking cap and nudges stay as they are. In general coding, the agent sees what its test runs already said, without paying for reruns, and spends some of those saved turns checking that the bug is fixed and not just its example.

evidence: Test plumbing, in passed and failed runs alike. test-runs-recover-cut-verdict-and-bad-la replayed this parent's 26 runs: 163 filtered test commands, 55 with no verdict shown (22 runs), and 38 of those followed directly by another test run with no edit in between (21 runs). Moments I read: django-14672 (passed) t22-t26. `tail` showed only "Destroying…", then came a grep rerun for `FAILED (errors=1)`, a `grep -B2 -A15 "^ERROR"` rerun, an `ls tests` to learn that `model_checks` is not a label, and a fourth run. django-15987 (failed) t15-t17 went the same way. django-13128 (passed) t24-t26 and t33-t34 involved bad labels `querysets`, `lookups_expressions`, then `conditional`, `values`. In the sibling lineage the same code (test-runs-show-cut-results-and-bad-label) kicked in on 50 of 51 runs, with requests 37→34, output tokens 21.9k→18.3k and minutes 7.4→5.4 (+2.0 ± 3.5 passes, unproven). Narrow fixes: in the diverged django-15987, the failing run's review weighed the second use of the same value (`app_dir in fixture_dirs`), then said "The issue only mentions the duplicate check. Minimal fix it is." The passing run normalized the value once, at the top. The probe variant's author also traces django-12273 (`uid=None` handled, `obj.pk = None` missed), sympy-13974, astropy-13977 and sphinx-7985 (failed in both parent runs) to a fix of the example's one path. "minimal" shows up in 13 of the 26 parent transcripts. I replayed this package. (1) Driving the real handlers of all three extensions in sequence on a Django-style runner, `runtests.py loader_tests 2>&1 | tail -3` (only "Destroying…" lines) came back with "Ran 4 tests / OK". With a bad label added, it came back with `FAILED (errors=1)` and "`loader`: tests/ has no loader/ or loader.py. Similar: loader_tests". A command whose verdict was visible got no note. (2) try-variant on a Path/str duplicate check with a second use in the same function. The agent covered both uses itself. The review with the probe fired, and the agent ran one script with 6 inputs (the second route, a tuple, a trailing slash). It changed nothing and stopped, one request later. Its grep-filtered test run showed the verdict, so test-feedback stayed quiet. (3) try-variant on a tag set that compares names case-sensitively in four methods. The agent fixed all four itself, and the probe ran two scripts and changed nothing. (4) try-variant on `take()` letting stock go negative, while another module writes the same private counter directly. The agent fixed only `take()`. The probe surfaced the second route ("orders.fulfil directly sets item._quantity") and the agent declined it, since the issue scopes the fix to `take()`. That is the intended guard against scope creep, so on wording like this the probe can surface a route without extending to it. Its pytest and unittest runs showed their verdicts, and test-feedback stayed quiet in all three real runs. Left out on purpose: the 4K reasoning cap (cap-reasoning-at-4k-per-response). In 7 of the 9 parent runs with a response over 4K, the task passed, and the parent's failures were judgment calls, not long deliberation.

predicts: "finish review with same-cause probe" on nearly every run with a change, and "changed the code after the review" on about 10-25% of runs, more than the parent's review produced. "added the test results a filter cut" on about 60-90% of runs, "explained missing test labels" on about 15-35%, mostly on runtests.py-style repos. Test runs that come right after a filtered run, with no edit in between, should fall well below the parent's 38 in 26 runs. Requests per task: about -3 from test feedback and +1-2 from the probe, about -1 to -2 net. Output tokens per task should fall about 5-12% and minutes per task by more, since the reruns it removes come late and at high context. Passes should rise by 1-3 of 51, mostly on tasks where the parent fixed only the example's path, with no loss elsewhere. It's wrong if passes fall while post-review changes show scope creep (new failures in existing tests, edits to sibling implementations or behavior the task didn't name). It's also wrong if requests and output tokens don't fall against the parent (the probe eating the savings), or if reruns after a filtered run stay as common.
