# Review the diff against the restated task once, before the run may end

hypothesis: The agent ends a run as soon as it believes its fix is right. By then the issue text is dozens of tool calls back, and in the failed runs the final diff quietly misses something the issue states (the title's requirement, the exact expected output) or was never tested after the last edit. With this change, the first time the agent tries to finish, the harness (agent_before_settle, once per run, never blocking) puts the task text and the real `git diff HEAD` (plus non-junk untracked files) side by side. It also says whether any test command ran since the last edit, and asks for one pass: map each stated requirement or expected result to a part of the change, run the issue's own example and compare output literally, run the changed code's existing tests if they haven't run since the last edit, and judge by the task and the repo, not a remembered upstream fix. If everything holds, the agent answers in two lines with no tools. Checking a change against the spec placed right next to it is cheap and helps in any repo.

evidence: Most of the parent's 19 failures are plausible, self-tested fixes that miss something the issue says. sphinx-9281 (diverged): the failed run printed `= ValueA` while the issue literally expected `MyEnum.ValueA`, and claimed it matched. django-12774 (diverged): the failed run deleted the uniqueness check entirely and ran no test after editing; the existing lookup tests cover it. django-13012 (diverged): the last turn raised the right concern, then dismissed it as "matches upstream exactly". django-15916: the diff never implemented the title ("allow ModelForm Meta to specify formfield_callback"). 9 runs edited code and ran no test command after the last edit (3 failed: 10973, 12774, 14404). Passed runs show the same recall-justified, eyeballed finishing, so chance often decides these. Replay on a small repo with the 9281 situation (Enum/Flag defaults with a literal expected rendering): the model was about to finish with `Perm.R | W` against an expected `Perm.R | Perm.W`, after writing "Yes!" it matched. The review made it reread the expected line, fix the code, rerun the example and the tests, then finish correctly. On a run that was already correct, the review cost one request (285 output tokens) and the run ended normally.

predicts: Acted on nearly every run: all 75 parent runs ended normally under the 100K-context skip threshold, so expect one "finish review" entry per run. One extra request where everything already holds, 2-5 where it runs the example or tests or fixes something; tokens up roughly 10-15% on passed runs. Some failed runs should change their diff in the review turn (fix a missed stated requirement, an output-format mismatch or a test breakage), so passes should go up. It's wrong if passes don't rise over the parent, or if review turns in failed runs almost always just reply "all holds" without changing the diff.
