# Bash test runs piped through a filter keep their summary and failing test names

hypothesis: The agent almost always pipes test runs through a filter (`runtests.py … 2>&1 | tail -5`, `| grep -E "^(OK|FAILED|Ran)"`). The filter often cuts the runner's verdict or the names of the failing tests: Django's runner prints "Destroying test database…" lines after the summary, and `FAILED (errors=4)` says nothing about which tests failed. So the agent reruns the same suite with a different filter just to see what it already ran. This variant changes the bash tool for these commands only. It inserts a `tee` before the first filter to keep the runner's unfiltered output in /tmp. When the filtered result is missing the verdict or the failing test ids, it adds them to the result (unittest/Django, pytest, sympy and a few other formats), along with the saved file's path. If the filter left no output at all, it adds the output's last lines instead. Anything else the agent sees is unchanged. Telling the agent the result of the run it just made should remove a rerun-only turn, and the waiting time that goes with it, whenever a filter hides the outcome. It needs no new tool for the model to adopt. That matters because run-tests-tool's separate tool was used but barely cut requests.

evidence: In the parent's 26 runs, 193 test-runner commands were piped through a filter. 62 of those results showed no verdict at all (ANSI stripped). 41 were followed directly by another test run, in 16 runs: sympy-14248 had 12, django-7530 had 5, and django-13128, django-14404 and sphinx-8593 had 3 each. django-7530 turns 35→36 show it: "The output got cut off at the tail end before displaying the OK/FAILED lines" leads to the same command again with `| grep`. cap-runaway-thinking's broken django-12273 does the same thing: "only the line about destroying the DB is displayed — I need the summary line. Let me re-run it". Another 50 or so results showed `FAILED (errors=N)` without naming the failing tests, e.g. django-12273 "Ran 302 tests … FAILED (errors=4)" and django-10973. Replaying the parent's commands through the rewriter: it would tap 166 calls and add a note to about 100 of them, in 22 of 26 runs (20 passed, 2 failed). In try-variant on a small repo with a Django-style runner, `python3 tests/runtests.py 2>&1 | tail -5` got back the cut "Ran 188 tests / FAILED (failures=1) / FAIL: test_…" lines. The agent then went straight to that test instead of rerunning the suite. Heredocs, loops, background jobs, `| head`, unbalanced quotes and a missing `tee` leave the command untouched.

predicts: Fewer test→test pairs where the second run only changes the filter or the tail length, fewer `git stash`-free reruns just to read a verdict, about 1–2 fewer requests in runs that run tests, and a few percent fewer output tokens. Pass rate should stay the same. It should rise slightly at most, where a run that rarely saw which tests it broke now sees them. The "acted" entry "added the test results a filter cut" should appear in most runs. The idea is wrong if the share of filtered test runs followed directly by another test run doesn't drop well below the parent's 41/193. It is also wrong if requests and output tokens per run don't fall, or if the agent spends new turns reading the saved logs.
