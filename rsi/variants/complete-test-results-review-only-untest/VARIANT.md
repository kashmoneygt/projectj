# Test runs come back with their full verdict, and the finish review runs only when the change is untested or its last test run failed

hypothesis: The agent pipes almost every test run through a filter (`| tail -3`, `| grep -E "^(Ran|OK|FAILED)"`). The filter often cuts the verdict or the failing tests' names, and guessed test labels that name no module look like ordinary errors, so the agent reruns the same suite just to read what it already ran. When it stops, the parent always adds a finish review. After a change whose tests passed, that review hardly ever changes the diff: it re-runs the example and the tests at the run's largest context, or turns into guessing what upstream did. This package merges two variants. test-feedback.ts (from test-runs-recover-cut-verdict-and-bad-la) puts the cut verdict and failing test ids back into the same result and names labels that match no test module. The gate from finish-review-only-on-untested-change keeps the review only for an objective gap: no change, no test since the last edit, or new untracked files. Merging them adds two points. (1) A test run counts only if it ran something: "No module named pytest", "Ran 0 tests", "no tests ran", "collected 0 items", file-not-found, or only label `_FailedTest` errors leave the change untested, and the review names that empty run. (2) Each run is judged by its result as the model saw it, test-feedback's recovered verdict included. If the last real test run after the last edit reported failures (label errors don't count), the review stays and asks the agent to settle each failure by the system prompt's rule on existing tests. That is the one situation where the parent's review changed a diff for a reason. A passing tested change ends at once. A failing or untested one still gets its second look.

evidence: Read start to finish: django-15987 both runs, sphinx-9281 failed, django-14672, sympy-12096, astropy-8872 and matplotlib-25332 passed, astropy-13977, sphinx-7985 and sympy-13974 failed. Only 3 of the parent's 26 runs edited after their first stop. django-10973 (passed) was untested and keeps the review. django-15987 (failed) had dismissed an existing test its change broke, and the review reverted that part; its last test run reported `FAIL:`, so the review stays. sphinx-7985 only moved a CHANGES bullet. In the passed runs the review re-ran the example and tests and changed nothing. django-7530 spent 3+ turns at 35% context re-proving a fix it had already tested. I replayed the gate over the parent's transcripts with this package's patterns. It skips the review in 16 of 26 runs. It keeps it in 3 untested runs (django-10973, django-14608, sympy-14248) and in 7 whose last test run failed: django-15987, plus six with failures that were there before the change (astropy-8872, django-16454, matplotlib-22871, scikit-learn-14710, sympy-12096, sympy-15976). In the 16 skipped runs, 29 of 475 turns (6.1%) came after the first stop, all at peak context. The empty-run check matched 22 test commands in 15 runs (15 `python -m pytest` with no pytest, 5 bad `runtests.py` labels, 2 others) and changes no gate decision on these runs. It decides the gate in a run like test-runs-recover-cut-verdict-and-bad-la's broken django-15987, whose only test after the edit was a bad label. Test feedback kicked in on 50 of 51 and 51 of 51 runs. On the grandparent it cut requests 37→34 and output tokens 21.9k→18.3k (+2.0 passes). Its port to this parent did not repeat that (35→37 requests, -1.5 passes). Both are within noise.

predicts: "skipped finish review: change tested and passing after last edit" on about 55-70% of runs. "finish review (failing tests)" on about 20-30% and "finish review (untested change...)" on about 10-15%. "added the test results a filter cut" on most runs and "explained missing test labels" on about 15-35%. Requests per task should fall by about 1-3 (about 1.1 skipped review turns per run on average, plus rerun-only test turns), and input tokens by more than output tokens, since the skipped turns are the largest. Passes stay within noise of the parent, and a dismissed self-caused failure still gets reviewed. It's wrong if passes drop by 2 or more per run, or if the skip share is high but requests and tokens per task don't fall against the parent.
