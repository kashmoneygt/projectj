# Steer the agent off reconstructing upstream fixes from memory, back to the repo's code

hypothesis: The agent treats most tasks as a known issue in a public project and spends its longest reasoning trying to recall "the actual upstream fix": ticket and PR numbers, commits, a later version's code. It can't check any of it, and much of it is invented. That's where runs go wrong. Either the recall rambles into a 20K–80K-token loop that ends with no tool call, or a made-up "upstream" becomes the yardstick and outweighs the issue text and the agent's own concerns. With this change, `APPEND_SYSTEM.md` tells it to work from the repo: a recollection is a guess to check, and the issue's stated behavior plus the existing tests are what the fix is judged against. `recall-guard.ts` enforces this where the behavior shows up. After a response whose reasoning tries to reconstruct an upstream fix, it appends a short note to that response's first tool result (at most 3 per run, at least 5 responses apart). If the response that would end the run leans on such a recollection, the agent gets one more turn to check the change against the task (once per run). That turn says "make the edit now" if no file was changed. Working from the code in front of you instead of an unverifiable memory is how coding goes in any repo. It should cut wasted reasoning and remove one source of confidently wrong fixes.
evidence: The shipped detector matches in 67 of the parent's 75 runs (48 of 56 passed, all 19 failed), first at response 3 (median). Matching responses are about 21% of all responses but hold 62% of output tokens in passed runs and 75% in failed ones. Diverged tasks, failing side: in django-12774 the agent deleted the uniqueness check "matching the upstream fix for ticket #29574" (an invented ticket) and never ran the existing tests. In django-13012 the last turn raised the right concern, then dismissed it as "matches the upstream Django fix (ticket #31050) exactly". In sphinx-9281 the agent wrote a `stringify` from a recalled "PR #10010" that prints `ValueA` where the issue expects `MyEnum.ValueA`, and kept it "consistent with upstream". In sympy-14248 one 79K-token response ("Have to rely on my memory of upstream fixes") ended with no diff, and matplotlib-22871 also ended with an empty patch while chasing "the upstream fix". The passing sides worked from the code. Passed runs waste tokens on it too: django-15037 spent most of its 56K output tokens recalling "#33309". The final response leans on recall in 5 of 19 failed runs (django-12774, django-14404, matplotlib-22871, sphinx-9281, sympy-14248) and in 2 of 56 passed runs (django-13033, psf__requests-6028). Replay on a `packaging` checkout with a planted bug: both the parent ("The actual upstream fix (packaging PR #520)") and this variant ("The upstream fix (around packaging PR #664)") recalled by their third response, so the prompt alone doesn't stop the habit. The note then fired on that tool result, no further recall followed, and the fix was correct.
predicts: "recall nudge" should fire on most runs (about 80–90%) and "recall check at finish" on about 5–10%. Recall phrases per run and the thinking share should drop. Output tokens per task should fall clearly, mostly in the long tail: fewer 10K+ responses, fewer reasoning-only endings and fewer runs with no diff. Passes should hold or rise, mainly on tasks whose failing runs were a recall-driven fix or a recall loop. It's wrong if responses matching recall per run don't fall against the parent (the model ignores both the prompt and the note), if output tokens don't fall, or if passes drop (recall was helping more than it hurt).
ports: review-diff-against-task-at-finish (the one-time check before the run ends, narrowed here to runs whose final reasoning leans on a recalled upstream fix)
