# Add a `trace` tool that runs a Python example and returns the call tree of repository functions it executed, with return values

hypothesis: Before editing, the agent finds where behavior comes from by grep and reading, and traces the code paths in its head: the parent's runs make a median of 7 grep/read/sed calls before the first edit, and only 8 of 26 runs run the issue's example before editing. When the wrong value is built in a layer below the first grep match, or comes through a second path, the agent fixes the layer it found, or spends many turns tracing paths by hand. The new `trace` tool runs a snippet under a profiler and returns its output plus a compact call tree of the checkout's functions that ran: who called whom, call counts, and the simple return values (str, number, bool, small containers; other objects show only their type name, so no project code runs during the trace). Long trees are cut by depth, and a `focus` regex shows the paths into one function. One line in the tool rules says when to use it: a runnable example gives a wrong value without a traceback, before the first edit. It says to skip it when a traceback already names the line, when there is nothing runnable, and for tests. So the agent picks the function to change from what actually ran, in one call instead of a chain of greps. That helps on any Python repository.

evidence: In sphinx-9281, the failed run fixed the signature formatter and got `ValueA`, which differs from the issue's literal `MyEnum.ValueA`. The passed run fixed the value-description function (`object_description`) that produced the text. A trace of the issue's example lists both functions with their return values. In django-12273, both runs spent about 30 requests reading and mentally tracing `save()` paths before the first edit (20 explore calls). The failed run missed the `pk = None` route. Long pre-edit exploration also shows in sympy-14248 (17 explore calls), sympy-15976 (13), django-13128 (15), sphinx-9281 (12) and sphinx-8593 (11), in both passed and failed runs. Tool tests: without the rule line, the model ignored `trace` on two small replays and localized by grep. With the rule line, on a copy of a 3.6K-line package with a bug two calls below the public API, it called `trace` in one of two runs, as its second action. That tree showed `_is_not_suffix x5 -> True` (also for `'post3'`) under `_compare_compatible`, the exact cause, and the run fixed that function. That run also used `trace` to check its edit and got about 10K chars per call, so after the first edit the default tree is now 40 lines: a replay got 8 depth-limited lines with `[+N nested]` marks. On an in-process pytest session (12.8K calls), the tracer took 0.3 s and returned a 108-line tree. Syntax errors, exceptions, `sys.exit`, `unittest.main()`, pickling, timeouts (the partial tree is kept) and "no repository code ran" all return a readable result.

predicts: "acted" entries ("trace tool run before|after the first edit") appear in at least 30% of runs, mostly before the first edit. Those runs make fewer grep/read calls before the first edit than the parent's median of 7. Fewer fixes land in a caller or sibling of the function that produces the wrong value, so passes are the same or better, with output tokens per task the same or lower. Uptake in testing was 1 of 2 runs, so this rests on the rule line being followed. The idea is wrong if uptake stays under 15% of runs, or if runs that use `trace` take more requests or tokens with no gain in passes.
