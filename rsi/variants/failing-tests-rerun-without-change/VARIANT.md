# Failing test runs after an edit get an automatic baseline: the harness reruns the same command with the change stashed and names new vs pre-existing failures

hypothesis: When a test run after its edit fails, the agent has to work out whether the failures are its own. It does that by hand: `git stash`, rerun, `git stash pop` (the parent's prompt tells it to), then compares two long outputs by eye or with ad-hoc grep/diff. Sometimes it forgets to pop. Now a `tool_result` hook steps in when a single-call bash test command fails after an edit. It reruns that exact command once with the tracked changes stashed (60-300 s timeout, pytest cache off), restores them, and checks that the diff is byte-identical. Then it appends one short note: the summary line without the change, plus which failing test ids appear only with the change, which fail without it too, and which fail only without it. Results are cached per HEAD+command, at most 6 runs. It never runs for commands that touch git state, write files or use `--lf`/`--ff`, for parallel calls, or after 40 min. Exact attribution in the same turn saves the round trips. It also stops the agent from chasing failures that were already there, and from waving off regressions it caused as "pre-existing".

evidence: Manual stash baselines show up in 13 of 26 parent runs (37 `git stash` commands), in passed and failed runs alike. Examples: sympy-14248 (11 stash commands over turns 41-80, diffing failure lists by hand), matplotlib-25332 (6 stash commands, the stash left unpopped at turn 36), django-7530 (ran the full suite twice to compare), astropy-8872, django-16454, sympy-12096, and the failed astropy-13977 and sphinx-7985. Replaying the trigger rules over the parent transcripts, it would have fired in 20 of 26 runs (18 passed, 2 failed: django-15987 and sphinx-7985), on about 49 distinct failing commands. In a try-variant run with the real model, it fired on the agent's first pytest run, which had a failure that existed before the change. The agent got "Failing without your change too, so not caused by it: tests/test_locale.py::test_utf8_locale" and moved on with no stash of its own. In mock replays the tree and stash came back intact in these cases: staged and new files, a baseline that writes into tracked files, a baseline that hangs past its timeout, an untracked file that blocks the pop, and a directory that isn't a git repo (skipped).

predicts: `acted` entries "reran failing tests without the change" or "showed the cached baseline for failing tests" on roughly 60-75% of runs. "baseline could not restore the change" should be about 0. The agent's own `git stash` commands drop sharply (from about 1.4 per run to under 0.5). Runs where it fires use 1-3 fewer requests, and tokens fall a little. Wall time goes up by one extra test run per distinct failing command: replayed on the parent's runs, that is about 10 s per run where it fires and 47 s at most. Passes hold or rise slightly. Signs it's wrong: manual stash baselines persist at similar rates; requests and tokens don't fall on runs where it fired; passes drop, for example final diffs that leave tests listed as "Failing only with your change" still failing.

ports: run-tests-tool (comparing test results with and without the change). It moves from a new tool that ran on a copy of the repo into a hook on the agent's own failing test commands, so it needs no new tool and no change to how the agent runs tests.
