# Run the finish review in a fresh context, without the agent's earlier reasoning

hypothesis: The parent's finish review runs in the same context that produced the change, so the agent re-reads its own rationale and confirms it ("matches upstream", "those tests encode the old bug, they'll be replaced") instead of checking the change. From the review message onward, this variant sends each request with only the system prompt, the task, and the review message plus what follows it. The earlier history is left out of the requests, not deleted from the session. The review message carries everything an outside reviewer needs: the `git diff HEAD` (stat + patch, up to 16K chars), untracked files, the test commands the agent ran, the tail of the last test output (and whether it ran after the last edit), and a checklist. The checklist steps are: map every requirement to a hunk; undo hunks no requirement needs; run the task's example and copy expected vs actual output word for word; run the existing tests for the touched code and fix the change, not the test, unless the test asserts the reported bug; change nothing without a concrete reason. Without the author's reasoning in view, the reviewer judges the change by the task and the repository, the way a code reviewer does. That catches scope creep into neighbouring code paths and regressions the author had already argued away, which happens on any codebase. The runaway-thinking guard, the 8192-token thinking cap and the nudges are the parent's, unchanged. With no git, or no change at all, there is no diff for an outsider to judge. The review then keeps the parent's in-context form, with the parent's 100K-token skip.

evidence: In all 26 of the parent's runs, plus the 8 runs where it fixed or broke a task against its own parent, the in-context review led to zero edits. It's a confirmation ritual, so the parent's gain came from the thinking cap, not the review. Its 3 failures each passed through that review with the flaw in view. In sympy-15976 the agent also changed the content printer, which the issue never mentions, and broke `test_content_symbol`. The review dismissed the failure as "old tests encoding the bug". The passing baseline run left that printer alone, and 5 of the 7 variants' failed runs of this task made the same extra change. In sympy-14248 a 201-line diff touched core arithmetic helpers and broke 11 tests, all dismissed, while passing runs changed only the printers (45-49 lines). In sphinx-9281 the review noticed that its output differed from the expected `MyEnum.ValueA` and dismissed it as matching a recalled upstream fix. I replayed this with the model against mock repos, using a multi-turn tool loop, at the review moment. A change that also edited an unrequested renderer and broke its test was reverted to the minimal diff in 3 of 3 samples. A correct fix whose only failing test pinned the reported bug was kept in 3 of 3 samples, so no false undo. A single-shot fresh replay of the sphinx moment still misread or recalled in 2 of 3 samples, which is why step 3 now asks for verbatim side-by-side output. End to end with try-variant on a synthetic repo, two runs ended cleanly with the correct diff, and the review request fell from ~4.3K to ~2.9K prompt tokens. A no-change run kept the in-context review, and a mock-API test covered no git, compaction, aborted runs and the "review changed the diff" record.

predicts: "fresh-context finish review" fires on almost every run. "review changed the diff" rises from 0 (the parent) to a few-to-10% of runs, mostly reverting unrequested hunks or fixing a literal expected-output mismatch. Tasks failed through scope creep or dismissed regressions (like sympy-15976 and sympy-14248) pass more often, and passes rise by 1-3 out of 51. Review-phase requests are a fraction of the parent's (system + task + review instead of the whole history), so input tokens on long runs fall. The reviewer adds about 2-6 calls to re-run the example and tests, so output rises slightly. It's wrong if "review changed the diff" stays near 0. It's also wrong if runs that passed in the parent start failing after a review change, i.e. the reviewer undoes needed parts or breaks a working fix for lack of context.
