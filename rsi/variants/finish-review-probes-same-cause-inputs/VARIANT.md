# Finish review makes the agent probe other inputs that hit the same cause, and extend a fix that only covers the task's example

hypothesis: Today the agent fixes the exact trigger in the issue's example, re-runs that example, sees it pass and calls the fix "minimal" and done. The parent's once-per-run finish review (requirements, example, tests) only re-checks that same example, so a fix that misses a second way into the same bug goes out unchanged. With this variant, when there is a change, the finish review gets one more step. The agent names the cause its change removes (the code that went wrong, not the symptom). It then picks 2-4 other inputs that reach the same code by another route and tries them in one short script. It looks first at other uses of the same value in the changed function or class, then at the same state reached another way (it greps the repo for other code that sets the same attribute or calls the same function), then at another type or form of the value, and at every function or option the task names. It extends the fix only where the problem the task reports still shows. It is told to stay on the task's code path: leave other backends, printers, formats and subclasses alone, add no unasked behavior, use inputs that are easy to build, run the script once, and leave other problems alone. In general coding this is the difference between "the reported example works" and "the bug is fixed". The step comes at the one moment the agent has the change, the repro and a working environment in hand.

evidence: In the parent, the runs that failed with a working fix for the example usually had too narrow a fix, not a wrong one. django-15987 (diverged): in its finish review the failing run narrowed its fix to the `len(set(...))` duplicate check and explicitly decided not to normalize the value in the second check (`app_dir in fixture_dirs`) of the same function ("Minimal fix it is"). The passing run normalized the value once, at the top. django-12273 (diverged): the failing run handled one way of resetting the key (`uid=None`) and missed the other way to reach the same state (`obj.pk = None`). The passing run tested both and added the second branch. sympy-13974, astropy-13977 and sphinx-7985 failed in both parent runs with a fix for the example's one path. Each passed once in the grandparent with a broader fix of the same cause, for example sympy fixing the Pow branch and `tensor_product_simp_Mul` as well as `_eval_power`. "Minimal" as the reason to stop appears in 15 of 26 parent transcripts. Counter-evidence I weighed: over-extension broke django-14672 (fix moved to the wrong method) and sympy-15976 (spread into a sibling printer), so the step keeps the probe on the task's path and only changes code where the reported problem reproduces.

Replays with try-variant on small /tmp repos, some with the parent on the same repo:
- Negative quantity, where the constructor, `restock()`, a compat alias and a CSV importer write the private attribute directly. The parent's review accepted a setter+constructor fix that still let the alias and the importer through. In the variant run that reached its review with that same narrow fix, the probe tried 5 routes, found `restock(-10)` still going negative and routed it through the validated setter. That recorded "changed the code after the review". Its reasoning explicitly weighed "another method that sets it" against "no unasked behavior". It missed the alias in another module, so I added "grep the repo for other code that sets the same attribute" to the step. In another run the review considered the remaining routes and declined them as a design call. In runs whose fix was already complete, the review ran one probe or stopped with no tool calls.
- Case-insensitive duplicates and a Path/str duplicate check: the agent covered the second place itself before the review, and the probe changed nothing (no over-extension). The first wording made one run spend 8 extra requests building a Path subclass and chasing an unrelated relative-path quirk. After the "easy inputs, run once, leave other problems" wording, the review cost +1 request and about +700 tokens over the parent's review on the same repo (+200 on another).

predicts: "finish review with same-cause probe" is recorded on nearly every run with a change, and most review turns should contain one probe script. The new observational entry "changed the code after the review" compares `git diff HEAD` at the review with the diff when the run settles again. It should be recorded on roughly 10-25% of runs, more than the parent's review produced. Results: +1 to +3 passes on tasks where the parent fixed only the example's path (multi-route bugs like those above), with no loss on single-route tasks. Cost: about 1-2 more requests and about 3-8% more output tokens per run. It's wrong if post-review code changes stay rare, if probe scripts don't appear, or if passes fall while post-review changes show scope creep (broken existing tests, edits to sibling implementations or to behavior the task didn't name).
