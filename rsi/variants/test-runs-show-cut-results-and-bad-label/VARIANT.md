# Bash test runs get back the verdict and failing tests a filter cut, and bad test labels explained, in one note

hypothesis: The agent runs tests through bash and almost always pipes them through a filter (`| tail -5`, `| grep -E "^(Ran|OK|FAILED)"`). The filter often cuts the verdict (Django's runner prints "Destroying test database…" lines after it), or shows `FAILED (errors=2)` without saying which tests failed. And when the agent guesses a dotted label that names no module (`models`, `values`, `auth`), the runner reports it as an ordinary-looking error. Then the agent reruns the suite only to see what it already ran, probes with `import <label>` or `git stash`, or takes empty output for "all pass". This package adds one bash `tool_result` hook to the parent that merges two variants. A `tee` before the first filter keeps the unfiltered output, and when the filter hid the verdict or failing test ids, the result gets them back (test-summary-survives-output-filters). Every label of a label-taking runner is checked against the files on disk, and a missing one is named along with the closest real labels (explain-missing-test-labels, unchanged). The two overlap on the `_FailedTest` errors that missing labels cause. Those are explained once, as label problems, and left out of the "failing" list. A failing test now counts as already shown only when its whole id is visible, so a real import error is never hidden behind a label note. With the outcome of the run it just made in front of it, the agent skips rerun-only turns and stops reading a label error or an empty filter as a result.

evidence: I replayed the parent's 26 transcripts through the merged code. The tap fires on test runs in 24 runs (67 calls). In 21 runs, 38 of those results showed no verdict at all, and 17 of those were followed directly by another test run (12 runs). In 5 runs, 10 results showed `FAILED (…)` without naming the failing tests. `_FailedTest` label errors appear in 7 of the 14 Django runs. Moments: in django-13012 at t14→t15, the agent got `FAILED (errors=2)` and reran the suite with `grep -B2 -A20 "^ERROR"` only to see the errors. They came from its labels `values` and `group_by`. Then at t16→t17, `tail -3` cut the verdict ("tail -3 cut off the results"), and it reran again. django-12273 passed but took 91 requests and 17 min. At t50, `tail -20` showed only "Destroying test database" lines. At t51–52, `models` gave "Ran 1 test … FAILED (errors=1)" and was rerun with `head`. At t60 and t84 more guessed labels (`auth`, `admin`, `db_migrations`) cost a turn each. In sympy-14248 (failed, 141 requests) at t70–71, `python -m unittest … | grep -i "fail\|error"` printed nothing and the agent concluded "test_str all pass!", but no tests had run. I replayed it live with try-variant on a small repo with a Django-style runner. The `tee` went in every time and the note stayed silent when the verdict was visible (2 runs). When `tail -5` showed only teardown lines, the note added "Ran 0 tests … OK", and the agent's next message said "0 tests were run in that label" (run 3). In offline replays, `lookups`, `text_utils` and `…BulkUpdateTest` were explained with the right labels, label errors weren't listed twice, and a real failure and a real import error in the same run were still listed. On its own, explain-missing-test-labels kicked in on 17/51 runs (it predicted 30–40%) for +0.5 tasks per run, not proven. test-summary-survives-output-filters has not been run.

predicts: "added the test results a filter cut" on most runs (60–90%), and "explained missing test labels" on about 15–35%, mostly on runtests.py-style repos. Test runs that only repeat the previous one with a new filter, tail length or `grep ERROR`, and `import <label>` probes after a label error, should drop well below the parent's rate (17 reruns after a result with no verdict, in 26 runs). That's about 1–3 fewer requests on runs that test, and more on long Django runs. Fewer late, high-context requests mean fewer input and output tokens. Passes should hold or rise slightly, where a run would otherwise misread a hidden or empty result. It's wrong if requests and tokens per run don't fall against the parent, if reruns right after a tapped run stay as common, if the agent spends new turns reading the saved logs, or if passes drop (for example, if real errors get waved off as label problems).
