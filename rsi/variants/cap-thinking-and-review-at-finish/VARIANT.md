# Cap reasoning at 8K per response and keep accidental endings going, then review the diff against the task once at the real finish

hypothesis: The parent's runs go wrong at their ending in two separate ways. In one, a single response thinks for 20K–113K tokens (recall or a counting loop) and the run ends with no real tool call or is cut at the output cap, often leaving no diff. In the other, the agent ends as soon as it believes its fix is right, and the diff quietly misses something the issue states (literal expected output, the title's requirement) or was never tested after the last edit. This package puts the two changes that each moved their behavior together in one extension (`finish-guard.ts`) plus `thinkingBudgets.medium = 8192`. Reasoning stops at 8K. A response that ends the run by accident (cut, reasoning-only, a tool call written as text) gets a short nudge to go on (at most 2 in a row and 4 per run), and looping or cut blocks are trimmed from the context. The first time the agent really finishes, it sees the task next to its `git diff HEAD`, whether a test ran after its last edit, and gets one requirement-by-requirement check. They share one `agent_before_settle` handler, so they don't both fire on the same stop the way two stacked extensions would. The accidental-ending nudge goes first, and the review waits for a real finish. A capped response that does answer counts as a real finish, so the review replaces the redundant "capped" nudge there. The review also keeps the task text from the first message, so it still works after a compaction has dropped that message (the ported version silently skipped the review then). Bounding one bad response and checking the final diff against the stated task both help in any repo, and they go after different failures, so their gains should add up.

evidence: Diverged tasks show both failure modes. sympy-14248 failed: a 79K-token counting loop ended with `</tool_call>` inside the reasoning, so there was no diff. matplotlib-22871 (23K) and django-14404 (113K, cut at the cap) went the same way. In the parent's 1,990 responses, 11 went over 8K, across 9 runs (6 failed). django-13089 passed but spent 25K tokens recalling an upstream ticket. On the finishing side, sphinx-9281 failed after printing `= ValueA` against the issue's literal `MyEnum.ValueA` and calling it a match. django-12774 failed after deleting the uniqueness check "matching upstream ticket #29574" with no test run after the edit. django-13012 raised the right concern and then dismissed it on recall. In the tree, cap-runaway-thinking scored +1.5 ± 2.1 (kicked in on 30/153 runs; output tokens 20.5k→18.6k, no-patch runs 1→0). review-diff-against-task-at-finish scored +1.2 ± 1.9 (146/153 runs; +13% tokens, about +3 requests). Its review turns in "broken" runs (django-15987, matplotlib-22871) left the diff unchanged, so the review itself didn't cause those losses. Both variants' fixed and broken lists are mostly the parent's noisy diverged tasks. Replays: a fake-event replay of the 14248 sequence trimmed the loop, nudged once, reviewed once at the real finish and ended. A capped answer before the review got the review and no nudge, a git failure or a compacted context still produced a review, and an aborted run was left alone. Live try on a small repo with an Enum/Flag expected-output issue: the review fired once, the agent reran the issue's example and the tests, and the run ended. A scratch copy with a 150-token budget showed `settings.json` cutting reasoning at 150 tokens and "reasoning hit the budget" being logged.

predicts: "finish review" appears on nearly every run. "reasoning hit the budget" appears on about 15–20% of runs, "continued after …" on a few percent, and never together with a review on the same stop. No response's reasoning goes over about 8.2K tokens. Runs with no patch or ending at the output cap go to about 0. Output tokens per task land near the parent's (cap −9%, review +13%) with about 3 more requests. Passes should rise by about the two gains together (+2 to +3 of 51), more than either part alone. It's wrong if passes don't beat both parent and the better single variant, if long reasoning responses still appear, or if tokens rise well above the review variant alone.
