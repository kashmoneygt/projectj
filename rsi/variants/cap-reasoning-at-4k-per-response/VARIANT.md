# Cap each response's reasoning at 4K tokens instead of 8K, so long single-response deliberation turns into a tool call sooner

hypothesis: Now a single response may think for up to 8,192 tokens before it has to act. The responses that use more than 4K are mostly not the agent's decisions. They are reconstructions of upstream tickets, commits and release notes, guesses about what tests will check, counting or identifier loops, and long mental execution of code that one command could run. Each costs minutes and stays in the context of every later request, because past reasoning is replayed. With the server stopping reasoning at 4,096 tokens, the model has to act with what it has: run the check, read the file, or make the edit. Its reasoning so far is still in context for the next response, so a real design chain carries on after one tool call instead of being lost. Fewer output tokens and minutes per task, with the same work done.

evidence: In the parent's 26 runs, 13 responses had more than 4,096 reasoning tokens, in 9 runs (7 passed, 2 failed). They are django-10973 t13 4.1K (ticket and commit recall) and t17 8.2K (counting loop); django-12273 t9 6.2K (commit dates, which led to a `git log` date check), t11 5.2K (release-note recall), t16 7.1K and t27 8.2K (repeating, trimmed by the guard); django-13128 t15 5.0K; django-7530 t15 8.2K (repeating recall of later source); matplotlib-22871 t7 5.5K (upstream PR recall); sphinx-7985 t6 4.9K ("what the hidden tests might look like"); sympy-13974 t3 4.1K; sympy-14248 t21 8.2K (loop); and sympy-15976 t15 8.2K. About two thirds are recall, test-guessing or loops. The rest are real design reasoning (12273 t16, 13128 t15, 13974 t3). Above 4,096 these responses held 29.9K of the 404.6K output tokens (7.4%). The decisions that lost the diverged runs (10973, 9281, 15987) were made in short responses of 2.7K or less, so the cap neither causes nor fixes them. In a try run on an Easter-date formula bug, the cap stopped a response at exactly 4,096 tokens in the middle of mentally evaluating the formula for one year. The model then wrote a script to check every term instead. Over 480 s the cap fired 5 times in 14 requests, and every capped response still made a tool call. The parent on the same repo hit its 8K cap once in 17 requests. Neither changed a file within 480 s, so in that window the cap cost no progress.

predicts: No response's reasoning goes over ~4.1K tokens. "reasoning hit the budget" shows up in about 25–35% of runs, against ~10% at 8K. Output tokens per task fall by 8–15% and minutes per task fall with them, mostly in the long tail (10K+ token runs). Requests per task rise by 0–1. The pass rate stays within noise of the parent. It's wrong if passes drop by 2 or more tasks per run, mainly on long design-heavy tasks where the cut lands mid-design. It's also wrong if output tokens per task don't fall by at least ~5%, which would mean the model just re-derives the cut reasoning in the next response.

ports: cap-runaway-thinking (the same server-side reasoning cap, set lower)
